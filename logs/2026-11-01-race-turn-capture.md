# 推理链 · 2026-11-01 · 剧本15 比赛回合训练数据抓取

> 本文件只记录**怎么想的**，不记录数据本身。数值放在数据仓，不混进来。
> 说明：以下是对当时判断过程的事后复述，不是逐字原始草稿；关键分支与自我否定都保留了。

---

## 0. 你问的那个「44444 怎么那么多」

先答这个，因为它解释了整份思考链的噪音来源。

```
444444 = 0x6C81C = 本局的 ObscuredInt 加解密 key
```

游戏把每个 int 都存成**两个字段**：

```
内存里：[ key = 0x6C81C ][ hidden = key ^ 真实值 ]
真实值 = hidden ^ key
```

所以**每一个** ObscuredInt 都会在转储里出现一次 `1c c8 06 00`（= 0x6C81C 小端）。
一个训练有 7 个 ObscuredInt，五个训练就是 35 次。看起来像"怎么全是 44444"，其实那是**同一把钥匙被反复打印**。

这也意味着：**key 每局变**，任何硬编码 key 的代码下一局必废。

---

## 1. 起点：从哪下手

**已知**：插件 3.28.8 在线，场景 15，用户说这回合是比赛（不刷队友）。

**先证伪再动手**：直接打 `/debug/params?all=1` → `items: []`、`actual_elem_class: unknown`。

> 第一反应是"这回合没有训练数据"。
> 但用户明确说"应该也有训练可以抓"，所以不能停在"端点为空"这个结论上。

**判断**：端点坏了 ≠ 数据不在。先去拿**原始对象**。

---

## 2. 找到对象图

`/debug/training_partners` 给出 11 个 `SingleModeCommandInfoData` 指针，
其中 5 个是训练：101 / 102 / 103 / 105 / 106。

**关键观察**：这 11 个对象的 `TrainingPartnerArray` 全是 `null`。

> 两种解释：
> a) 数据没加载
> b) 这回合确实没有队友（比赛回合）
>
> 选 b，因为 5101（演目）的 `TrainingPartnerArray` 有 3 个元素 —— 说明**数组机制本身是好的**，只是训练项没有。
> 这个对照很重要：它把"全局失效"排除掉了。

---

## 3. 找字段偏移（不是猜的）

`/debug/cmdinfo` 直接把 `SingleModeCommandInfoData` 的字段表吐出来了：

| 字段 | 偏移 |
|:--|:-:|
| CommandType | 0x10 |
| CommandId | 0x24 |
| IsEnable | 0x38 |
| TrainingPartnerArray | 0x50 |
| TipsEventPartnerArray | 0x58 |
| **ParamsIncDecInfoArray** | **0x60** |
| FailureRate | 0x68 |

> 注意：这里的步长是 **0x14**（0x10→0x24→0x38），不是 0x04 或 0x08。
> 一个 ObscuredInt 占 20 字节（key4 + hidden4 + fake4 + 填充），所以相邻字段隔 0x14。
> **如果按普通 int 算偏移，后面全错。** 这是第一个容易翻车的点。

---

## 4. 逐级解引用

```
命令对象 (0x76C7916900 等)
  +0x60 → ParamsIncDecInfoArray (数组对象)
        +0x18 → length
        +0x20 + i*8 → 元素指针
```

验证：106 的数组 length = 4，元素 4 个，地址连续（`A140/A180/A1C0/A200`，每个 0x40）。

> 元素大小 0x40（64 字节），不是 0x14。
> 因为它是**引用类型对象**：对象头 16B + 两个 ObscuredInt（各 20B）+ 填充。

每个元素只有两个字段：

| 偏移 | 含义 |
|:--|:--|
| 0x10 | Type（ObscuredInt） |
| 0x24 | Value（ObscuredInt） |

> 第二个字段在 0x24 而不是 0x20 —— 因为第一个占了 0x10–0x23。
> 我一开始按 0x20 读，读出来是 `0`，一度以为"字段不存在"。

---

## 5. 验证点：用已知答案反查

**先用 106 试**，因为历史记录里它下层合计应该是 **25**。

解出来：体力+5、SP+7、智力+12、速度+1 → 合计 **25** ✅

> 这一步是整个抓取的**锚点**。如果解出来不是 25，说明解码链路有错，后面全不用看。
> 它同时否定了历史假设"25 = 8 + 17" —— 实际是 12+7+5+1。

---

## 6. 假设被推翻的地方

把同样的方法套到 102/103/105，出现两个矛盾：

### 矛盾一：负数

`Type=10` 的条目解出 **-21 / -22**。
两个不同训练取值几乎相同 → 不像真实数值，更像占位或另一种语义。

**处理**：不下结论，标记为未解。**没有**因为"整数就该是正的"去改解码方式 —— 那是拿结论倒推。

### 矛盾二：主属性对不上

按"101速 102耐 103力 105根 106智"的旧认知：

| 命令 | 旧认知 | 解出来的主项 |
|:-:|:--|:--|
| 102 | 耐力 | 力量 +13 |
| 103 | 力量 | 毅力 +17 |
| 105 | 根性 | 耐力 +13 |

**主项全错位。**

> 第一反应是"解码错了"。但 106 已经验证过 25，解码链路是对的。
> 所以错的是**命令 ID → 训练种类的映射**，不是解码。

**修正后的假设**（按主项反推）：

| 命令 | 主项 | 推断种类 |
|:-:|:--|:--|
| 102 | 力量 +13 | 力量 |
| 103 | 毅力 +17 | 毅力 |
| 105 | 耐力 +13 | 耐力 |
| 106 | 智力 +12 | 智力 ✅ 已验证 |
| 101 | ？ | 速度（排除法） |

> 这个表**尚未被游戏画面证实**，只是自洽。列出来是为了下次带着它去验，不是当结论。

## 7. 死路：101 没拿到

101 的数组指针拿到了（`0x76C790F5A0`，length=4），但元素地址指向 `0x76C7CB6B70` 一带，
读出来是 `klass 0x7518C799A0` + 一个二级指针 —— 继续跟下去，落到的是 **UI 字符串表**（`OBJ_clr_txt_trainingmenu00` 之类）。

**判断**：101 的 `ParamsIncDecInfoArray` 元素与另外四个**不是同一种容器**，或者这一项在本回合尚未填充真实数据。

**处理**：停手。继续沿着不确定的指针链深挖，风险是读到别的对象还当成数据 —— 那比"没抓到"糟得多。

---

## 8. 自我核对的三条

1. **锚点法**：先用已知答案（25）验证链路，通过后才批量套用。
2. **对照法**：用"5101 有队友 vs 训练项没队友"排除"数组机制失效"。
3. **止损法**：101 连读两层都是异类结构，立即停，不硬凑五训齐全。
